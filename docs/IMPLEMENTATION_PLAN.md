**Last updated:** 2026-08-01

## 1. Overview

IDE Bridge (IDEBP) is a protocol and daemon that lets AI agents communicate with VS Code and JetBrains IDEs through a unified, IDE-independent, language-independent, versioned, capability-oriented, revision-aware protocol over loopback WebSocket.

See `TASK.md` for the authoritative product scope. This plan operationalises the TASK.md phases into trackable work with concrete acceptance criteria and validation commands.

> **Adapter dependency note:** Adapter *implementation* may begin after Phase 1 (protocol types and schemas exist). However, adapter *integration testing* with a real daemon requires Phase 2 (daemon + bridge-client). Phases 3 and 4 are listed as depending on Phase 2 because they cannot be marked complete without integration evidence.

### Phase 1 — Protocol

**Status:** Completed (2026-08-01; audited after remediation)

**Current increment (2026-08-01):** The authenticated `bridge/handshake` contract and the complete
MVP catalog are represented by 29 wire-schema documents: 24 request/response pairs, 14
notifications (including `$/cancelRequest`), and 22 normalized errors. A separate fixture schema
validates deterministic language expectations without entering the wire catalogue. Ajv compiles all
159 top-level and `$defs` entries. Type generation produces 138 exported TypeScript declarations
from canonical wire schemas, and CI checks fixture compatibility and generated-file freshness. The
29 manifest fixtures include handshake edge cases, representative valid/invalid contracts, and
language-specific TypeScript, Java, and PHP expectations. Automated tests validate and round-trip
all 64 public message forms, exercise every normalized error code, preserve URI wire shapes, and
cross-check expected symbol ranges and rename paths against the real deterministic source projects.
The audit corrected capability-dimension applicability, structured error invariants, wire/test
schema separation, runtime schema packaging, and CI pnpm/build ordering. See
`docs/evidence/phase-1-audit-2026-08-01.md` and ADR-0005.

**Deliverables:**
- JSON Schema 2020-12 files for every request, response, event, and error
- TypeScript types generated from schemas (via `scripts/generate-types.ts`)
- Protocol version negotiation types
- Authenticated session establishment via `bridge/handshake` before any other application message;
  session roles are `adapter` and `consumer`, while `ide/register` remains adapter-only
- Capability model types (`support`, `guarantee`, `atomicity`)
- Document and revision types (`editorVersion`, `contentHash`, `workspaceEpoch`)
- Symbol handle and locator types
- Edit plan, precondition, and undo token types
- Notification types (all MVP notifications from TASK.md §12)
- Error code constants and structured error types (all from TASK.md §14)
- ADR-0005 for operation-dependent capability dimensions
- Readiness state types
- Protocol JSON fixtures (valid and invalid examples for schema validation, distinct from the deterministic example projects below)
- Deterministic example projects per TASK.md §23:
  - `examples/typescript-project/` — class, interface, implementation, multi-file references, overload/multiple signatures, Unicode symbol, rename test target
  - `examples/java-project/` — interface, abstract class, implementation, override method, references, multi-file rename target

- Scripts: `scripts/check-protocol-fixtures.ts`, `scripts/generate-types.ts`

**Acceptance criteria:**
1. Every public request, response, event, and error has a schema.
2. All valid examples pass schema validation.

8. Position encoding (utf-16) is explicit in types.
9. **Protocol independence:** `packages/protocol` has zero imports from `vscode`, `@types/vscode`, JetBrains SDK, or any Serena code. This is verified by an automated check (e.g., ESLint `no-restricted-imports` rule or a script that greps for forbidden import sources in `packages/protocol/src/`).

### Phase 2 — Daemon & Client

**Status:** In progress (Phase 1 completed and audited)

**Current increment (2026-08-01):** The audited security/discovery foundation provides private token
and discovery handling on Unix. The audited transport increment now adds an IPv4 loopback-only
WebSocket server on `/rpc`, bounded frames and handshake time, canonical pre-dispatch validation,
generic authentication failures, constant-time token matching, discrete version negotiation,
role/topology-bound sessions, and a transport-neutral authenticated connection abstraction. See
`docs/evidence/phase-2-discovery-audit-2026-08-01.md` and
`docs/evidence/phase-2-handshake-transport-audit-2026-08-01.md`. The shared client now validates
private discovery metadata, opens a bounded no-redirect WebSocket, authenticates adapter or consumer
roles, validates and correlates the canonical daemon response, and exposes typed handshake failures;
see `docs/evidence/phase-2-client-handshake-audit-2026-08-01.md`. Its audited application engine now
maps all 23 method contracts and 14 notifications to canonical runtime validators, provides typed
outbound calls and notification handlers, validates method-correlated responses, maps normalized
errors, and implements per-request timeout and `$/cancelRequest` emission; see
`docs/evidence/phase-2-client-rpc-audit-2026-08-01.md`. Windows discovery ACL support is explicitly
rejected until implemented. The composed daemon now maintains session/adapter/workspace/capability
and readiness state, answers registry-local methods, routes the nine read-only workspace operations
with per-hop ID rewriting, enforces role and symbol-handle ownership, broadcasts authorized events,
and propagates cancellation, timeout, and disconnect cleanup; see
`docs/evidence/phase-2-session-routing-audit-2026-08-01.md` and ADR-0006.
Prepare/apply/discard/undo routing is now intercepted by a bounded store with daemon-owned consumer
identities, private adapter identities, expiry/invalidation, atomic one-shot apply/discard/undo,
capability and workspace-trust gates, and strict result checking; see
`docs/evidence/phase-2-plan-store-audit-2026-08-01.md` and ADR-0007.
The shared client now accepts the thirteen routed methods on authenticated adapter sessions through
a typed, singular handler API. Protocol-owned role partitions govern both directions; bounded actual
handler execution, per-request `AbortSignal`, atomic settlement, crossed-cancellation grace, and
method-specific result/error validation protect the inbound boundary. See
`docs/evidence/phase-2-adapter-dispatch-audit-2026-08-01.md` and ADR-0008. Reconnection is now
available through an opt-in discovery-file facade that rereads rotated metadata, retries with
bounded exponential backoff and jitter, preserves typed handlers, restores adapter state before
publication, and never queues or replays application work; see
`docs/evidence/phase-2-client-reconnection-audit-2026-08-01.md` and ADR-0009.
Daemon-owned WebSocket heartbeat now keeps quiet healthy sessions alive through automatic pong
frames and expires only peers that miss bounded complete response windows. One shared unref'ed
timer, bounded cadence/threshold configuration, canonical close reasons, registry activity refresh,
and the existing route/plan/session cleanup path are covered by ADR-0010 and
`docs/evidence/phase-2-heartbeat-session-expiration-audit-2026-08-01.md`. Structured logging now uses
a closed event catalogue, process-local HMAC request correlation, monotonic durations, bounded
emission, and failure-contained JSON-lines sinks under ADR-0011.
The `@ide-bridge/cli` package now exposes the real `ide-bridge` binary with foreground daemon
ownership, private discovery publication, signal-safe cleanup, authenticated `status`, `adapters`,
and `workspaces` commands, plus read-only `doctor` checks for discovery, permissions, PID, port,
protocol, adapter readiness, and stale sessions. ADR-0012 defines output and exit-code semantics.
Unix Phase 2 functionality is locally complete; Windows discovery ACL support remains explicitly
unsupported rather than approximated.

> Adapter implementation may begin after Phase 1 (protocol types exist), but full integration testing requires this phase (daemon + bridge-client).

**Parallel subtracks:**

**Subtrack 2a — Daemon (`packages/bridge-daemon`):**
- WebSocket JSON-RPC 2.0 server (loopback only, dynamic port)
- First-message `bridge/handshake` processing: validate without dispatch, constant-time token
  comparison, role/topology binding, version selection, then session creation; reject and close on
  any failure
- Token generation (>= 256 bits), private discovery file
- Authentication, session management, heartbeat, expiration
- Session registry (adapters, sessions, workspaces, capabilities, readiness)
- Request routing by `adapterId` / `workspaceId` / `sessionId`
- Plan store (in-memory, with expiration, invalidation, atomic consumption, cleanup)
- Cancellation support via `$/cancelRequest {id}` (JSON-RPC 2.0 standard cancellation; the daemon cancels in-flight requests and notifies the adapter)
- Timeouts, message size limits
- Structured, redacted logging
- CLI: `daemon`, `status`, `adapters`, `workspaces`, `doctor`
- Transport abstraction for future UDS/named pipe/tunnel

**Subtrack 2b — Shared TypeScript Client (`packages/bridge-client`):**

Per TASK.md §17, the bridge-client must provide:
- Daemon discovery (read and parse discovery file)
- Authentication (`bridge/handshake` using `authentication.method: "token"`)
- Reconnection (automatic retry with backoff)
- Typed JSON-RPC calls (request/response with full type safety from Phase 1 types)
- Notifications (send and receive)
- Timeouts (per-request configurable)
- Cancellation via `$/cancelRequest {id}`
- Version verification (protocol negotiation at handshake)
- Runtime validation (incoming message validation against schemas)
- Typed errors (mapped from protocol error codes per TASK.md §14)

The VS Code extension (Phase 3) must use this client. JSON-RPC code must not be duplicated in the extension.

**Acceptance criteria:**
1. Non-loopback connections refused.
2. Unauthenticated connections refused.
3. Any first application message other than a valid `bridge/handshake` request is rejected before
   routing and the connection is closed; both adapter and consumer roles establish sessions.
4. Multiple simulated adapters route correctly.
5. Multi-workspace routing works.
6. Session expiration and heartbeat work.
7. Plan expiration, invalidation, and one-time consumption work.
8. Reconnection works.
9. Cancellation via `$/cancelRequest {id}` works; timeouts work.
10. Discovery file has restrictive permissions.
11. No token, file content, or source text in logs.
12. Oversized messages rejected.
13. `doctor` checks all required health points.
14. bridge-client can discover, authenticate, and make typed requests to the daemon.
15. bridge-client reconnection works after daemon restart.
16. bridge-client cancellation via `$/cancelRequest {id}` works.

```bash

pnpm --filter @ide-bridge/bridge-daemon typecheck
pnpm --filter @ide-bridge/bridge-client test
```

### Phase 3 — VS Code Adapter

**Status:** Completed (2026-08-02; verified in a real VS Code 1.131.0 extension host)

Current increments: ADR-0013 defines the desktop extension boundary, one-window/multi-root workspace
model, trust mapping, opaque identities, epoch changes, URI preservation, and unsaved-buffer
revisions. ADR-0014 adds the autonomous CommonJS bundle, validated configuration, authenticated
discovery/manual-endpoint connection, local Unix daemon auto-start through the bundled CLI,
`ide/register`, current-state restoration after rotation, and awaited unregister/shutdown. ADR-0015
adds native `document/read` and `document/getRevision`, exact unsaved-buffer revisions,
handler-before-capability publication, daemon-side document scope validation, coalesced document
opened/changed/saved/closed events, and truthful workspace root transitions. ADR-0016 adds
provider-backed `document/getSymbols`, exact hierarchical/flat symbol mapping, revision-coherent semantic
snapshots, physical-session-bound handles, immediate handle invalidation, and daemon-side recursive
handle/locator authority checks. ADR-0017 adds `workspace/searchSymbols`: multi-root provider-backed
search, protocol-owned search bounds and URI containment, a separate FIFO handle namespace that never
revokes document handles, scope/kind filtering distinguished from truthful `truncated` reporting, and
generalized daemon bound/authority validation for search results. Search handles deliberately carry no
verified revision, which makes controlled locator relocation a blocking prerequisite of the symbol
navigation increment. ADR-0018 closes that prerequisite and adds `symbol/resolveAt`,
`symbol/getDefinition`, `symbol/getReferences`, and `symbol/getImplementations`: semantic-identity
relocation (amending ADR-0003, whose fingerprint rule could not survive a moved symbol), fail-closed
`STALE_SYMBOL`/`AMBIGUOUS_SYMBOL` outcomes, a transient handle namespace shared with search,
`Location`/`LocationLink` mapping with root filtering, utf-16-only position handling, and daemon
authority checks for all four methods. ADR-0019 adds `diagnostics/getSnapshot` and
`diagnostics/changed`: a snapshot scoped to documents the editor holds open — the only ones with a
truthful `editorVersion` — with `truncated` reporting, shared count ceilings, non-destructive
mapping that never clips a message, debounced change events, end-to-end redaction evidence, and
daemon containment for both the snapshot and the notification. ADR-0021 adds two-phase renames:
adapter-held one-shot plans, precondition re-verification immediately before writing (the daemon
never checks content), workspace trust enforced at both phases, save-after-apply with hashes taken
once the save settles, and `workspace/undo` declared unavailable because VS Code exposes no way to
revert an applied workspace edit. ADR-0022 closes the event surface: `document/deleted` now carries
identity without a revision, `workspace/trustChanged` announces a trust grant without invalidating
anything else, rename/delete events are projected only for documents the editor can observe, and an
invalidation-only filesystem watcher covers external disk changes. ADR-0023 closes the phase with a
inspected VSIX and an end-to-end suite executed in a real VS Code 1.131.0 extension host, driven by
the Phase 1 language contract — which it falsified on one point (see the update log). Remote daemon
auto-start and Windows discovery ACL support remain explicitly unsupported rather than approximated.

**Deliverables:**
- VS Code extension using official API
- Daemon discovery/auth via shared `bridge-client` (no duplicated JSON-RPC code)
- Adapter registration (`ide/register`), workspace registration, clean deregistration (`ide/unregister`)
- Capability announcement (dynamic, provider-presence-aware via `ide/getCapabilities`)
- Workspace registration and listing (`workspace/list`)
- Document operations: `document/read`, `document/getRevision`, `document/getSymbols`
- Symbol operations: `workspace/searchSymbols`, `symbol/resolveAt`, `symbol/getDefinition`, `symbol/getReferences`, `symbol/getImplementations`
- Diagnostics: `diagnostics/getSnapshot` via `vscode.languages.getDiagnostics()`
- Refactoring: `refactor/prepareRename` via `vscode.RenameProvider.prepareRename`
- Plan application: `workspace/applyPlan` via `WorkspaceEdit` / `workspace.applyEdit`
- Plan discard: `workspace/discardPlan` (discard plan state, invalidate handles)
- Undo: `workspace/undo` (via VS Code undo mechanism when available; return undo token from `workspace/applyPlan`)
- Unsaved-buffer-aware revision hashing
- Workspace trust enforcement
- Event connections (open, change, save, close, rename, delete, folder change, trust change)
- Configuration settings (auto-start, manual endpoint, discovery path, log level, provider timeout)
- No public-network listen option

**Acceptance criteria:**
1. Extension is buildable (`vsce package` or equivalent dev build).
2. E2E TypeScript fixture scenario passes against `examples/typescript-project`.
3. Multi-file rename works.
4. Stale document returns `STALE_DOCUMENT` or `PRECONDITION_FAILED`.
5. Missing provider returns `CAPABILITY_UNAVAILABLE`.
6. Untrusted workspace blocks writes, returns `PERMISSION_DENIED`.
7. Unsaved buffer revision reflects in-memory content.
8. `workspace/discardPlan` invalidates the plan and associated handles.

### Phase 4 — JetBrains Adapter

**Status:** In progress (started 2026-08-02)

The phase covers the scope of Phases 2 and 3 combined, in Kotlin, and is therefore planned as
increments: **4a** protocol types and wire conformance (done, ADR-0024), **4b** discovery and
authenticated handshake (done, ADR-0024), **4c** transport, real daemon
integration, registration, workspace model, and dumb/smart readiness (done, ADR-0024; the platform
boundary is compile-checked only until 4h), **4d** documents and revisions, **4e** symbols
and `SmartPsiElementPointer` handles, **4f** diagnostics, **4g** two-phase rename, **4h** real IDE
validation. Two capabilities VS Code could not offer should become real here and are to be verified
in their increments: `UndoManager` for `workspace/undo`, and `DumbService` making `INDEX_NOT_READY`
and the `indexing` readiness state truthful rather than simulated.

**Deliverables:**
- Kotlin IntelliJ Platform plugin (application service + project service)
- Daemon connection via WebSocket client (using bridge-client protocol types; the JetBrains plugin is Kotlin and does not import the TypeScript bridge-client, but must conform to the same protocol)
- Symbol handle registry (smart PSI pointers, locators)
- Request router, PSI-to-IDEBP DTO mapper
- Readiness manager (dumb/smart mode mapping)
- Plan manager
- Minimal diagnostics component (see below)
- Adapter registration (`ide/register`), workspace registration, clean deregistration (`ide/unregister`)
- Capability announcement via `ide/getCapabilities`
- Workspace registration and listing (`workspace/list`)
- Document operations: `document/read`, `document/getRevision`, `document/getSymbols`
- Symbol operations: `workspace/searchSymbols`, `symbol/resolveAt`, `symbol/getDefinition`, `symbol/getReferences`, `symbol/getImplementations`
- Diagnostics: `diagnostics/getSnapshot`
- Refactoring: `refactor/prepareRename`
- Plan application: `workspace/applyPlan`
- Plan discard: `workspace/discardPlan`
- Undo: `workspace/undo`
- Threading: no heavy PSI on EDT, read actions, write commands, smart mode waits
- Rename via JetBrains refactoring API

**Minimal diagnostics component:**

- **Source:** `DaemonCodeAnalyzer` — the JetBrains daemon-based analysis engine that runs inspections and annotators.
- **Limits:** Only diagnostics currently available from `DaemonCodeAnalyzer` at the time of the snapshot are returned. This is not a full inspection run. Diagnostics may be incomplete if the daemon has not yet analyzed a file (e.g., file just opened, dumb mode). The snapshot reflects the current highlighting state, not a fresh full analysis.
- **Timing:** Diagnostics are available after the daemon has processed the file. During dumb mode, diagnostics may be stale or unavailable.
- **Difference from full inspection:** `DaemonCodeAnalyzer` provides real-time feedback from registered annotators and inspections. It does not run all inspections exhaustively.
